### Dubbo3.x
3.x改了什么->应用级服务发现->Triple协议->云原生->面试高频题
### 3.x的演进背景
```
// Dubbo 2.x 的问题（大规模集群下）：
// ① 接口级服务发现：每个接口注册一个节点
//    → 一台机器几十个服务 × 几百个实例 = 上万节点
//    → 注册中心存储 + 推送压力大（推送风暴）

// ② 协议私有：dubbo 协议不通用，云原生生态不兼容

// ③ 不够云原生：难与 K8s/Service Mesh 集成

// 3.x 的三大演进：
// ① 应用级服务发现（核心）
// ② Triple 协议（HTTP/2，兼容 gRPC）
// ③ 云原生（K8s、Service Mesh）
```
### 应用级服务发现
2.x：接口级发现
```
ZK 注册数据（接口级）：
/dubbo/UserService/providers/
    ├── dubbo://192.168.1.10:20880?...
    ├── dubbo://192.168.1.11:20880?...
    └── ...（每个接口 × 每个实例）

问题：
① 一个应用有 50 个接口 → 50 个目录，每个都存所有实例
② 一次实例变更 → 触发 N 个接口的推送
③ 大规模集群（万实例）→ 注册中心存储爆炸 + 推送风暴
```
3.x：应用级发现
```
注册数据（应用级）：
/services/order-service/
    └── 192.168.1.10:20880    （一个应用一条，所有实例）

结构分两层：
① Provider 向注册中心注册"应用 + 实例列表"
② 元数据中心存储"应用 → 接口列表"的映射

Consumer 调用流程：
① 订阅应用（如 order-service）
② 拿到实例列表（应用级，量小）
③ 从元数据中心查"该应用提供哪些接口"（接口映射）
④ 完成调用
```

|维度|2.x 接口级|3.x 应用级|
|---|---|---|
|**注册单位**|接口|应用|
|**数据量**|接口数 × 实例数|应用数 × 实例数|
|**推送**|接口变更推送|应用变更推送|
|**大规模**|撑不住|显著缓解|
|**兼容 K8s**|难|天然对齐（K8s 也是应用级 Service）|
```
// 记忆：应用级 = K8s 的 Service 思路
// 一个"应用"对应一组"实例"
// 接口信息放元数据中心（接口 → 应用 的映射）
```
```
# 配置（3.x）
dubbo:
  registry:
    address: nacos://...
    register-mode: instance    # 应用级注册
  application:
    name: order-service
```
### Triple协议
```
// Triple：Dubbo 3.x 的新协议
// ① 基于 HTTP/2（像 gRPC）
// ② 兼容 gRPC（可互通）
// ③ 支持三种流式通信：
//    - Unary（一元，传统请求响应）
//    - Server Streaming（服务端流）
//    - Bidirectional Streaming（双向流）
```
为什么需要流式
```
// 传统 RPC：一请求一响应（Unary）
// 流式场景：
// ① 大文件/大数据分块传输
// ② 服务端持续推送（如行情、日志流）
// ③ 双向实时通信（如聊天）

// 类比：
// Unary = 普通 HTTP 请求
// Streaming = WebSocket 式的长连接流
```

|协议|传输|序列化|流式|
|---|---|---|---|
|**dubbo**（2.x）|TCP 自定义|Hessian2|❌|
|**Triple**（3.x）|HTTP/2|Protobuf（可换）|✅|
|**gRPC**|HTTP/2|Protobuf|✅|
```
// Triple 的定位：
// Dubbo 协议的"云原生替代品"
// 兼容 gRPC 生态，走标准 HTTP/2（网关/代理友好）
```
### 云原生与ServiceMesh
K8s集成
```
// 3.x 可以把 K8s 当注册中心（不用 ZK/Nacos）
// 应用级发现天然对齐 K8s 的 Service/Endpoint 模型
```
ServiceMesh
```
方案一：Java Agent 模式
    应用不用改代码，通过 Agent 把流量代理到 Sidecar

方案二：Proxyless 模式
    Dubbo 直接对接 xDS（Istio 控制面），不需要 Sidecar
    → 兼顾 Mesh 的治理能力 + Java 应用的性能
```
```
// Proxyless 是亮点：
// 传统 Mesh：所有流量经 Sidecar（多一跳，性能损失）
// Proxyless：Dubbo 直接从 xDS 拿规则（无 Sidecar，性能好）
```
